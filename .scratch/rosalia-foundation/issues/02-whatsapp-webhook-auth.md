## Agent Brief

**Category:** bug
**Summary:** The WhatsApp POST webhook must verify Meta's signature, fail closed, and acknowledge only after a unique provider event is stored.

**Current behavior:**
GET checks the verify token. POST parses JSON with no `X-Hub-Signature-256` check, then ingests and runs Rosalía inside the request. The catch block logs failures and still returns 200. The caller chooses the apparent sender and text.

**Desired behavior:**
Read the raw bytes once. Verify HMAC-SHA256 with the app secret using a constant-time compare after length checks. Missing secret, missing/malformed/invalid signature, or one flipped byte is rejected with zero ingest. A valid signature for the wrong receiving phone or WABA is not processed. Persist a unique provider event and enqueue a job in one transaction, then acknowledge. Duplicates acknowledge success without a second effect. A failure before persistence is retryable (not 200). LLM work happens on the job, not in the webhook request. Restart after acceptance resumes from durable jobs.

**Key interfaces:**
- App secret is distinct from the GET verify token
- Unique key is provider + receiving account + provider event id
- Existing Postgres `Job` table is the queue; no Redis

**Acceptance criteria:**
- [ ] Missing/invalid signature and one changed byte of a signed payload are rejected with zero database/provider calls
- [ ] A valid signature succeeds
- [ ] A valid signature for an unrelated receiving account is not processed by the wrong account
- [ ] Repeated and concurrent delivery of one event produces one accepted event and one logical effect
- [ ] A database outage before acceptance does not return a false success
- [ ] Restart after acceptance resumes processing from durable state

**Out of scope:**
- Opening or closing the WhatsApp send allowlist
- Building Direct's shop-to-customer number
